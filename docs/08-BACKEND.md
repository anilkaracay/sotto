# 08 · Backend

Stack per D-12: Next.js route handlers, PostgreSQL 16, Drizzle ORM with SQL migrations, a Node worker. All request bodies validated with `zod`. All timestamps `timestamptz` in UTC.

## 1. The golden rule for data

The database must never contain: plaintext payment amounts, salaries, balances, budgets, notes about money, or any key material. Amount bearing data exists only as ciphertext (disclosures, encrypted blobs to the owner). A schema test fails the build if any column name matches `amount|salary|balance|budget|gross|tax|net` outside the allow list: `proof_records.threshold_base_units` and `chain_activity.public_amount_base_units`. Both hold amounts that are already public onchain (proof thresholds, confidential deposit and withdraw amounts; ENGINEERING-RULES.md rule 4).

Implementation (step 1.2): Drizzle schema `packages/db/src/schema.ts` and SQL migrations generated by drizzle-kit in `packages/db/migrations`, applied with `pnpm --filter @sotto/db migrate`. Phase 1 creates the tables of step 1.2; `payroll_runs` (with the foreign key of `payments.run_id`) arrives in Phase 2 (step 2.3, migration 0005), `access_log` with the grant holder and activation columns and `payments.settled_at` in step 2.4 (migration 0006, which sets `settled_at` of the payments settled before it to their last update and `activated_at` of the active grants to their creation), `chain_activity`, `reconciliations` and the indexer's cursor on `token_accounts` in step 2.5 (migration 0007), and the other tables with the features that need them. Physical rules beyond the logical schema: wallet and address columns hold base58 (32 to 44 characters); `country` is two uppercase letters; `viewer_keys.public_key` is 32 bytes and every Ed25519 signature column 64 bytes; one active viewer key per user; one recipient per org and wallet; approval policies at least 1; approvals of kind `message` carry the message and its signature, of kind `execution` the execution signature; `period` grants need `period_from <= period_to`; `sessions.id` is the HMAC of the cookie token, never the token. Technical table outside the logical schema: `rate_limits(key text pk, window_start, count)`, the shared counters of section 6.

Row access is enforced in the API layer with one helper `requireMembership(orgId, roles[])`. Every query that reads org data goes through it. Write a test per endpoint for forbidden access.

## 3. API

All endpoints under `/api`. Errors: `{ "error": { "code": "...", "message": "..." } }` with correct HTTP status. The message is also the HTTP reason phrase (the RPC client reads only that). Codes used by the foundation (step 1.2, `apps/web/lib/server/errors.ts`): `invalid_request` (400), `unauthenticated` (401), `forbidden` and `forbidden_origin` (403), `payload_too_large` (413), `unsupported_media_type` (415), `rate_limited` (429 with `Retry-After`), `internal_error` and `server_misconfigured` (500), `approval_policy_not_available` (422), and `sign_in_invalid` and `sign_in_expired` (401, step 1.3). Every response carries `x-request-id`.

Auth
- `POST /auth/nonce { wallet }` returns a sign in message (domain, statement, nonce, issued at, expiration 5 minutes).
- `POST /auth/verify { wallet, message, signature }` verifies Ed25519, nonce unused and unexpired, sets the session cookie.
- `POST /auth/logout`, `GET /me`.
- Implementation (step 1.3, `apps/web/lib/server/auth.ts`, `app/api/auth`, `app/api/me`):
  - `POST /auth/nonce { wallet }` returns `{ input, message }`. `input` holds the `solana:signIn` fields: `domain` (the host of `NEXT_PUBLIC_APP_URL`, never taken from the request; on Vercel preview deployments only it is derived from `VERCEL_URL` at build time), `address`, `statement` "Sign in to Sotto. This request does not send a transaction or cost any fees.", `uri` (that origin), `version` "1", `nonce` (16 random bytes, hex), `issuedAt`, `expirationTime` (5 minutes later). `message` is the same fields as Sign-In With Solana text, built by `@solana/wallet-standard-util` `createSignInMessageText`, for wallets without `solana:signIn` (D-15). The nonce is stored in `auth_nonces` for that wallet.
  - `POST /auth/verify { wallet, message, signature }` (base64): the signed text is parsed with the util's parser and must name the configured origin (never the request's Host header), the wallet, the statement, version 1 and the issued nonce, with issue and expiry times exactly 5 minutes apart, no Not Before, Request ID or Resources, and nothing outside the canonical text of its fields; a Chain ID added by the wallet is tolerated. The Ed25519 signature is checked before the nonce is consumed, so bad signatures cannot burn a pending nonce; the nonce is then consumed atomically (unused, unexpired, same wallet and expiry). The user is created on first sign in and the session cookie set. Failures are 401 `sign_in_invalid` (the message or signature does not match) or `sign_in_expired` (replayed or expired, AC-01.2).
  - `POST /auth/logout` sets `sessions.revoked_at` and clears the cookie (204, AC-01.3).
  - `GET /me` returns `{ user: { id, wallet, displayName }, memberships: [{ orgId, orgName, orgStatus, role }], isAdmin }`.

Organizations and people
- `POST /orgs`, `GET /orgs/:id`, `PATCH /orgs/:id` (owner).
- Implementation (step 1.4, `apps/web/lib/org.ts`, `lib/server/orgs.ts`, `app/api/orgs`):
  - `POST /orgs { legalName, country, registrationNo, website, contactEmail, displayName? }` (session, write limits) creates the org as `pending_review`, the caller's `owner` membership and the `org_policy` defaults in one transaction and returns 201 `{ org }` (AC-02.1). Step 4.6 (D-30): on the devnet configuration the org is created `active` instead, with `reviewed_at` now and no `reviewed_by`; the org view's `verification` is `automatic` for it, `review` after an admin's decision and null while in review. Validation is shared with the onboarding form: trimmed text without control characters; legal name at most 200 characters and 400 UTF-8 bytes (it is attestation data, section 5); country one of the 249 ISO 3166-1 alpha-2 codes (`apps/web/lib/countries.ts`); registration number at most 64 characters; website an `http` or `https` URL with a domain name; contact email at most 254 characters; the display name defaults to the legal name; unknown fields such as `status` are refused. A wallet owns at most one org: 409 `org_exists` "This wallet already has an organization" (the unique index on `orgs.owner_user_id`).
  - `GET /orgs/:id` (any active member) returns `{ org, roles }` with `cache-control: no-store`.
  - `PATCH /orgs/:id` (owner, membership checked before the body): any subset of the create fields. The fields the admin reviewed (legal name, country, registration number, website) change only while the org is `pending_review`, otherwise 409 `org_details_locked`; the display name and the contact email stay editable.
- `POST /orgs/:id/invites { role }`, `POST /invites/:token/accept`.
- Implementation (step 1.8, recipient invites only, `apps/web/lib/server/invites.ts`, `app/api/orgs/[id]/invites`, `app/api/invites/[token]`; AC-07.3, 07 section 7):
  - `POST /orgs/:id/invites { role: "recipient", recipientId }` (money gate, owner, before the body; write limits): a recipient who joined already is 409 `recipient_joined`, an unknown one 404 `recipient_not_found`. The token is 32 random bytes in base64url (43 characters); the table stores only its SHA-256, so a copy of the database cannot accept invites. The link expires after 7 days, and a new link replaces the recipient's open one. 201 `{ invite: { url, expiresAt } }` with `cache-control: no-store`; `url` is `NEXT_PUBLIC_APP_URL` plus `/app/invite/<token>`, and the page shows it once.
  - `GET /invites/:token` (no session needed, auth limits per IP): `{ invite: { org: { id, displayName }, status, details, expectedWallet, acceptedByYou } }`, where `status` is `open`, `expired`, `accepted` or `unavailable` (the org is not active). Since step 1.8.1 (founder) `details` (`{ role, recipient: { displayName, roleTitle, wallet }, expiresAt }`) is set only for a session with the invited wallet, and `expectedWallet` (the invited wallet) only for a session with another wallet; without a session both are null. An unknown or malformed token is 404 `invite_not_found`.
  - `POST /invites/:token/accept` (session, write limits): in one transaction that locks the invite, it checks the invite (404 `invite_not_found`, 409 `invite_accepted`, `invite_expired`, `invite_unavailable`) and the wallet: the session's wallet must be the recipient's, otherwise 403 `invite_wrong_wallet` "This invite is for the wallet <address>. Sign in with that wallet." (the full address: an error message is also the HTTP reason phrase, which must be Latin-1, facts J1). It then adds or restores the `recipient` membership, links the recipient row to the user, creates the `own_payslips` grant (`active` when the user already has an active viewing key, `pending_viewer_key` otherwise) and marks the invite accepted. 200 `{ accepted: { orgId, role, grant: { status } } }`.
- Accountant invites (step 2.4): an accountant invite is made only with its grant (`POST /orgs/:id/grants` below) and has no recipient. `GET /invites/:token` gives it `role: "accountant"` and, while it is open, for any signed in session (the link is the holder's; no wallet is known before they accept), and for its holder once they accepted, `details: { role, scope, periodFrom, periodTo, grantExpiresAt, expiresAt }`: what the grant offers and the link's own deadline (founder, step 2.5 confirmation), nothing else, never the holder's name as the owner typed it or any amount, payment or recipient (founder, 2026-09-29; `apps/web/test/api-grants.test.ts`); a recipient invite has `role: "recipient"` and the details of step 1.8.1. `status` is `withdrawn` when the grant was revoked or expired before acceptance. `POST /invites/:token/accept` for an accountant invite locks the grant: withdrawn is 409 `invite_withdrawn` "The organization withdrew this invite", the org owner's own wallet 409 `invite_own`; otherwise it adds or restores the `accountant` membership, sets the grant's viewer, makes it `active` with `activated_at` when the user has an active viewing key and `pending_viewer_key` otherwise, marks the invite accepted and logs `grant_activated` or `grant_accepted`; 200 `{ accepted: { orgId, role: "accountant", grant: { status } } }`.
- `PUT /orgs/:id/policy { paymentApprovalsRequired, payrollApprovalsRequired }` (owner, step 1.2.1): integers of at least 1; the hackathon build accepts only 1 and refuses higher values with 422 `approval_policy_not_available`, "Approval policies above 1 are not available in this build" (D-04). Membership is checked before the body.
- Admin: `GET /admin/orgs?status=`, `POST /admin/orgs/:id/approve`, `/reject`, `/suspend`.
- Implementation (step 1.4, `app/api/admin/orgs`, D-09): only wallets in the `admins` table (403 otherwise; `ADMIN_WALLETS` only seeds that table). `GET /admin/orgs?status=pending_review|active|suspended` (no status: all) lists orgs oldest first with the owner wallet and the reviewer, at most 200, with `truncated`. The decisions are one conditional update each, which also records `reviewed_by` (the admin wallet) and `reviewed_at`: approve moves `pending_review` to `active`; reject moves `pending_review` to `suspended` (the hackathon build has no separate rejected status, D-09); suspend moves `active` to `suspended`. Any other starting status is 409 `org_status_conflict` (for example "Only in review organizations can be approved; this one is active"), so a suspended org cannot be approved again in this build; an unknown org is 404 `org_not_found`. The worker's `sas-issue` job then issues or closes the attestation (section 4).
- Money gate (AC-02.2, AC-02.4): every money endpoint (F-03 to F-09) authorizes with `requireMoneyAccess(db, session, orgId, roles)` instead of `requireMembership` alone: the role check first (403 `forbidden` for non members), then 403 `org_not_active` unless the org is `active` ("Money features open once Sotto verifies the organization" while in review, "Money features are disabled while the organization is not verified" when suspended). Each money endpoint's tests include these cases.

Keys and accounts
- `POST /viewer-keys { publicKey, signature }`, `GET /users/:id/viewer-key`.
- Implementation (step 1.5, `apps/web/lib/server/viewer-keys.ts`, 07 section 5): `POST /viewer-keys` (session, write limits) takes base64 of exactly 32 and 64 bytes, checks that the signature is the caller's wallet signature of `sotto-view-key-register/v1\n<base64 key>` (400 `viewer_key_signature_invalid` otherwise, nothing stored), and in one transaction marks the active key `rotated` and inserts the new one (201); the key that is already active answers 200 and changes nothing; a concurrent registration that loses the one active key per user index is 409 `viewer_key_conflict`. `GET /users/:id/viewer-key` returns `{ viewerKey: { id, userId, wallet, publicKey, signature, status, createdAt } }` with `cache-control: no-store`, to the user and to an owner of an org the user is an active member of (403 otherwise; 404 `viewer_key_not_found` without an active key). The browser verifies the signature before it encrypts to the key (I-8). Since step 1.8 the registration also activates the user's `pending_viewer_key` grants in the same transaction (07 section 5); since step 2.4 with `activated_at`, each logged as `grant_activated` in its org, and a grant whose expiry passed is not activated (the `grant-expiry` job expires it).
- `POST /token-accounts { address, keyScheme }`: the server verifies onchain that the account exists, belongs to the caller's wallet, uses the configured wUSDC mint and has the confidential extension before storing.
- Implementation (step 1.7, `apps/web/lib/server/token-accounts.ts`, `app/api/token-accounts`): `POST /token-accounts { orgId, address, keyScheme }` is a money endpoint: `requireMoneyAccess` with the owner role, so non members and other roles get 403 `forbidden` and an org in review or suspended 403 `org_not_active`, before the chain is read (AC-02.2). The body names the org because the money gate needs it. `keyScheme` is `standard_v1` only (D-03); the scheme cannot be read from chain. The server's RPC (`RPC_URL`) reads the account, which must exist, be a Token-2022 account of the caller's wallet for the cluster's wUSDC mint and have an approved `ConfidentialTransferAccount` extension; otherwise 422 `token_account_invalid` with the reason ("The token account does not exist onchain", "The account is not a Token-2022 token account", "The token account belongs to another wallet", "The token account does not hold this network's wUSDC", "The token account is not configured for confidential balances", "The token account is not approved for confidential balances"), and nothing is stored. The row records the slot of that read as `configured_slot`. 201 with `{ tokenAccount }` when new; 200 with the same row when the caller recorded it before; 409 `token_account_taken` when another user did; 503 `confidential_unavailable` when the cluster has no wUSDC mint (localnet without `LOCALNET_USDC_MINT`). The cluster is the server's (`NEXT_PUBLIC_CLUSTER`, read at runtime, `apps/web/lib/server/cluster.ts`). Since step 1.8 a recipient of the org records their own account the same way (roles owner and recipient); when the recorded account is the caller's associated wUSDC account, the account readiness is defined on and payments go to, the same read sets the caller's recipient readiness in that org (AC-07.3), and any other account leaves readiness as it is.

Wallet diagnostics
- `POST /wallet-reports` (step 1.7, `apps/web/lib/server/wallet-reports.ts`; session, write limits): one structured warning line `wallet_report` with the user ID, the wallet's name, the Wallet Standard version it declares and the versions of the features Sotto used (`solana:signMessage`, `solana:signTransaction`; the Wallet Standard gives apps no wallet app version), for `signature_not_deterministic` (the determinism check before account setup, 06 section 3), `compute_budget_changed` (the changed budget fields and values), `transaction_changed` (what changed; the transaction was not sent, 06 section 9) or, since step 1.7.1, `funding_split` (wrap and deposit did not fit in one transaction of the wallet's version: the version, the combined size and the limit, 06 section 4). The body is strict: no other fields, no free text beyond a short description, never keys, signatures or amounts. 204; nothing is stored. It is not a money endpoint: it reads and writes no org data.

Recipients and screening
- `GET/POST/PATCH/DELETE /orgs/:id/recipients`.
- `POST /orgs/:id/recipients/:rid/readiness` re-checks chain state.
- Implementation (step 1.8, `apps/web/lib/recipient.ts`, `lib/server/recipients.ts`, `app/api/orgs/[id]/recipients`; AC-07.1, AC-07.2, AC-07.4): money endpoints with the owner role, the gate checked before the body; writes have write limits.
  - `GET /orgs/:id/recipients` returns `{ recipients: [{ id, displayName, roleTitle, team, country, wallet, joined, readiness, readinessCheckedAt, privateBlob, invite: { status: none | pending | accepted, expiresAt } }] }` ordered by name, `cache-control: no-store`.
  - `POST /orgs/:id/recipients { displayName, roleTitle?, team?, country?, wallet, privateBlob? }`: trimmed text (name 1 to 120 characters, role and team at most 80, empty means null), an ISO 3166-1 alpha-2 country or null, a base58 wallet address, and `privateBlob` in base64 of 48 to 2048 bytes: a sealed box the owner's browser made of the canonical JSON `{ v: 1, default_amount, notes }` (base units as a decimal string or null, text or null) to the owner's own viewing key, which the server cannot open. Unknown fields such as `defaultAmount` are refused. The readiness is read from chain at once with the server's RPC (below); if it cannot be read the row starts as `no_account` with no check time, for the job to fill. 201 `{ recipient }`; the same wallet twice in an org is 409 `recipient_exists`.
  - `PATCH /orgs/:id/recipients/:rid` changes any of those fields except the wallet (refused as unknown). `DELETE` removes a recipient who has not joined, with its open invites (204); a joined recipient is 409 `recipient_joined` ("removing a joined recipient is not available in this build"). Another org's recipient is 404 `recipient_not_found`.
  - `POST /orgs/:id/recipients/:rid/readiness` reads again and returns `{ recipient }`; 503 `readiness_unavailable` when the chain cannot be read or the cluster has no wUSDC mint.

The page states why a recipient who is not ready cannot be paid confidentially (AC-07.4).
- `POST /orgs/:id/screen { wallets[] }` calls the provider (D-10); stores results; returns `clear | hit | error`.

Payments and payroll
- `POST /orgs/:id/payments { recipientId, idempotencyKey }` creates a draft.
- `POST /orgs/:id/payroll-runs { title, period, idempotencyKey, lines:[{ recipientId, idempotencyKey, privateBlob }] }` (step 2.3; each line's amount is its own sealed blob, the run has none).

- `GET /orgs/:id/activity?limit=` (step 2.5, the overview's recent activity; owner; `limit` 1 to 50, default 8): the org's latest payments of both kinds, newest first: `{ payments: [{ id, kind, run: { id, title } | null, recipient: { displayName, wallet }, status, errorCode, createdAt, settledAt, privateBlob, readers: [{ name, via: recipient | grant }] }], items, manifests }`: `readers` names who besides the owner holds the payment's record (the recipient, and each holder of a readable grant); `items` and `manifests` are the owner's own records of these payments, as `GET /orgs/:id/disclosures` gives them.
- Access log (step 2.4, F-14, AC-14.1, AC-10.5; `packages/db/src/access-log.ts`, `apps/web/lib/server/access-log.ts`, `app/api/orgs/[id]/access-log`): the web server and the worker write events through one function, `insertAccessEvent`, inside the transaction of the change they record; it refuses metadata with any key named like an amount (the golden rule's pattern, at any depth, `forbiddenMetadataKeys`), so a row never holds an amount. Events: `grant_created`, `grant_invite_renewed`, `grant_accepted`, `grant_activated`, `grant_backfilled`, `grant_revoked`, `grant_expired`, `disclosure_batch_created`, `payment_executed` and `payment_settled` (single payments), `payroll_executed`, `payroll_run_stopped` and `payroll_run_settled`, `approval_recorded`, and since step 2.5 `export_created` and `reconciliation_updated`; their metadata are ids, counts, kinds, scopes, statuses, dates, slots and filters. Since step 2.8 `proof_issued` (subject `proof`, the record address; metadata the expiry), whose label is the proof's counterparty label. An export's subject is the grant it was made under, so the log names its holder. `GET /orgs/:id/access-log?days=` (money gate, owner; `days` 1 to 90, default 7): the org's events of those days, newest first, at most 100: `{ events: [{ id, action, actor: { userId, displayName, wallet } | null, subject: { type, id, label }, metadata, createdAt }] }`, `cache-control: no-store`; `actor` is null for the worker, and `label` is read now from the subject: a grant's holder (or its recipient's name), a payment's recipient, a run's title.
- `GET /health` (step 1.2): `{ "status": "ok", "database": "ok" }`, or 503 with `{ "status": "degraded", "database": "unavailable" }`; no session, no rate limit, no configuration detail.

Job loop (step 1.4, `apps/worker/src/jobs/runner.ts`, `src/main.ts`): each job runs on its own interval and never overlaps itself; a failed run is logged (`job_failed`) and retried at the next interval; SIGTERM or SIGINT stops the loop after the running jobs finish. `node src/index.ts --once` (the package's `start` script plus `--once`) runs each job one time and exits 1 if one failed. At start the worker needs `RPC_URL`, `DATABASE_URL`, `SAS_SIGNER_KEYPAIR`, `SAS_CREDENTIAL_ADDRESS` and `SAS_SCHEMA_ADDRESS`, and on a local ledger optionally `LOCALNET_USDC_MINT` (step 1.8); 429 responses are retried as "network busy, retrying". Step 4.3: with `DEVUSD_MINT_AUTHORITY_KEYPAIR` and devUSD in the devnet registry, the `devusd-faucet` job (every 3 seconds) mints the faucet's requests: it checks once that its RPC serves devnet and that the mint's authority is its key (else it fails the open requests with `wrong_cluster` or `wrong_authority`), stores each signature and last valid block height before it sends, follows a sent request until it finalizes, and sends again under a new blockhash only once the old one expired. Step 4.6 (D-31): with `SOL_FAUCET_KEYPAIR`, the keypair file of a wallet that does nothing else, the `sol-faucet` job (every 3 seconds) sends the faucet's SOL grants from that wallet as plain System Program transfers, with the same order of signing, storing and sending as the mints: it checks once that its RPC serves devnet (else it fails the open requests with `wrong_cluster`), and it reads its wallet's balance before each grant and fails one that would leave less than the reserve of 0.1 SOL (`faucet_low`, logged as `sol_faucet_low` for the operator).

`sas-issue` (`apps/worker/src/jobs/sas-issue.ts`) polls the orgs table every 5 seconds, 10 orgs per pass:
- An `active` org without `attestation_address`: derive the attestation address (credential, schema, nonce = owner wallet), issue the `sotto.business.v1` attestation if none exists there (data `org_id`, `legal_name`, `country`, `verified_at` = `reviewed_at` in Unix seconds, `level` 1 when an admin decided (`reviewed_by` is set) and 0 for an org verified automatically on devnet (D-30, `attestationLevel`); expiry 365 days from now), then store the address (AC-02.3). An existing attestation for the same org is reused, so a crash between the chain write and the database update repairs itself. An existing attestation there with another `org_id` is left alone and logged as `sas_issue_conflict` (error level) for manual resolution; it can happen only when a database is reset while the chain keeps an attestation for the same owner wallet.
- A `suspended` org with `attestation_address`: close the attestation if it still exists (its rent returns to the SAS signer), then clear the address (AC-02.4). The address is stored even if the org was suspended while its attestation was being issued, so this step closes it.
- Tested on localnet against the SAS program cloned from devnet (`apps/worker/test/sas-issue-localnet.test.ts`, in the `ci:local` localnet job): issue, read back, the longest accepted legal name, level 0 for an org no admin decided on, idempotence, close on suspension. The level's rule also has a unit test (`apps/worker/test/sas-level.test.ts`).

`confirm-executions` (`apps/worker/src/jobs/confirm-executions.ts`, step 1.9): every 5 seconds the job reads, with history, the status of the transfer signature of each unsettled attempt (sent or confirmed, or ended `failed_clean` by the page less than 3 minutes ago, 100 per pass). Finalized without an error: the attempt `finalized`, the payment `settled` with the slot and the attempt's signatures. An error: the attempt `failed` with `onchain:<error>`, an executing payment `failed` (the page then closes the proof accounts and records `failed_clean`). Confirmed: the attempt `confirmed`. Not found 3 minutes after the attempt started: its blockhash has expired, the attempt `failed` as `transfer_not_found`. A transfer that lands after the page gave up is settled, never sent again (I-7). With nothing to check it makes no RPC call. Since step 2.4 the settlement also sets `payments.settled_at` and, for a single payment, logs `payment_settled { slot, attemptNo }`; the `payroll-runs` job logs `payroll_run_settled { lines }` and a run it stops as `payroll_run_stopped { status, by: "worker" }`.

`grant-expiry` (`apps/worker/src/jobs/grant-expiry.ts`, step 2.4, 07 section 7): every hour, with no RPC call, up to 100 grants `active` or `pending_viewer_key` whose expiry passed; each in its own transaction becomes `expired`, its records are deleted and `grant_expired { deleted, scope }` is logged with no actor. Tested with a test database (`apps/worker/test/grant-expiry.test.ts`).

`proof-program-health` (`apps/worker/src/jobs/proof-program-health.ts`, step 1.9): every 5 minutes it simulates a `VerifyPubkeyValidity` instruction with its proof inline for a throwaway ElGamal keypair (`checkProofProgram` in `@sotto/sdk/confidential`; nothing signed or sent; the worker's funded signer is the simulation's fee payer) and stores the verdict per cluster (the genesis hash, facts H6) in `cluster_health`, logging `proof_program_unavailable` on a failure. An RPC that cannot be reached is no verdict: it logs `proof_program_check_unreachable` and stores nothing, so the last result ages out. The banner of F-19 comes in step 2.8. Tested with a fake check and on localnet (a success).

`recipient-readiness` (`apps/worker/src/jobs/recipient-readiness.ts`, step 1.8): every 60 seconds the job reads up to 100 recipients that are not `ready`, least recently checked first, fetches their associated wUSDC accounts in one `getMultipleAccounts` and stores the readiness and the check time (the same rule as the API, section 3). The wUSDC mint comes from the cluster of the RPC's genesis hash: devnet from the cluster config, a local ledger derived from the optional `LOCALNET_USDC_MINT` (without it the job waits and logs `recipient_readiness_no_mint`); mainnet is not checked. With nothing to check it makes no RPC call. Tested with an RPC stand in and on localnet (`apps/worker/test/recipient-readiness-localnet.test.ts`: a configured account is ready, a plain wUSDC account not set up, a missing one no account).

`pending-credits` (`apps/worker/src/jobs/pending-credits.ts`, step 1.7): the worker's cluster comes from the RPC's genesis hash (devnet, mainnet, otherwise localnet; facts H6), read once. Every 60 seconds the job reads the recorded accounts of that cluster in batches of 100 (`getMultipleAccounts`), takes the public `pendingBalanceCreditCounter` and `maximumPendingBalanceCreditCounter` of the confidential extension and flags or clears. An account that no longer reads as configured keeps its state and is logged (`pending_credits_unreadable`). Nothing is applied: the flag only prompts the owner (AC-04.3). With no recorded account it makes no RPC call. Tested with an RPC stand in and on localnet (`apps/worker/test/pending-credits-localnet.test.ts`: flagged after 4 deposits into an account with a maximum of 5, cleared after the owner applies).

Public activity table (add to schema): `chain_activity(id, org_id, signature, slot, block_time, instruction_type, counterparty_address, public_amount_base_units null, destination_ciphertext bytea null)`. Public amounts exist only for deposit and withdraw, which are public onchain (facts A2); they are allowed in the column allow list with this justification. For each incoming confidential transfer, `destination_ciphertext` stores the raw destination ciphertext bytes (public data, allowed; see `07-SELECTIVE-DISCLOSURE.md` section 3).

As built (step 2.5, migration 0007): `chain_activity(id bigint identity pk, org_id fk, token_account, signature, slot, block_time null, instruction_index, instruction_type enum(account_setup, deposit, apply_pending, transfer_out, transfer_in, withdraw, wrap, unwrap, public_transfer_out, public_transfer_in), counterparty_address null, public_amount_base_units null, created_at)`, one row per top level instruction of a finalized transaction that touched the org's account, unique per (org, account, signature, instruction). A check keeps `public_amount_base_units` set exactly for deposits and withdrawals and never negative, so no other amount can be stored (ENGINEERING-RULES.md rule 4): the amounts of wraps, unwraps and public transfers are public onchain but not kept. `destination_ciphertext` is not built: it serves money in, which is Post-hackathon (M1). Base58 checks on the accounts and the signature.

`index-accounts` (`apps/worker/src/jobs/index-accounts.ts`, step 2.5, M4): every 15 seconds, the token accounts that orgs' owners recorded for their org on the worker's cluster (the genesis hash, facts H6; mainnet is not read during the beta, D-01), 20 per pass, the least recently read first. For each: the finalized signatures newer than its cursor (`getSignaturesForAddress` with `until`, pages of 1000, at most 10 pages per pass; more is logged as `index_accounts_backlog`), read oldest first; a failed transaction is skipped without being fetched; the others are fetched with `getTransaction` as base64 with `maxSupportedTransactionVersion: 1` (a version 1 transaction is refused without it, facts M3) and classified with `activityOf` of `@sotto/sdk/chain`, which decodes legacy, version 0 and version 1 messages (`decompileTransactionMessage`) and reads Token-2022's and Token Wrap's top level instructions (facts M1, M2); a version 0 transaction with lookup tables is logged as `index_accounts_lookup_tables_skipped` and not read. Rows are inserted once; the cursor moves to the last transaction read, with its slot, so one listed but not returned yet is read in the next pass. A node that no longer has the cursor transaction (purged from its ledger) refuses it as `until` (facts M5): the job logs `index_accounts_cursor_pruned` and lists the account back to the cursor's slot instead, that slot included (rows are inserted once); when nothing newer is found it drops the signature and keeps the slot, and later passes list the transactions after that slot. An account whose reading fails is logged as `index_accounts_account_failed`, marked read so it does not hold the head of the queue, and read again in a later pass; the other accounts of the pass are still read. A recipient's own account, recorded for the org, is not the org's and is not read. With no org account recorded it makes no RPC call. Tested with an RPC stand in (`apps/worker/test/index-accounts.test.ts`, the pruned cursor and a failing account included) and on localnet with version 0 and version 1 transactions (`apps/worker/test/index-accounts-localnet.test.ts`).

## 5. SAS setup

- One Sotto credential per cluster with the worker's attestation signer as authorized signer. Created by the worker's `bootstrap:sas` (in `apps/worker` because of D-24). Credential name `sotto`. On devnet and localnet the SAS signer is the credential authority, its only authorized signer and the payer of every SAS transaction; mainnet uses the KMS backed signer (section 5 of 14).
- Schema `sotto.business.v1` fields: `org_id` (string), `legal_name` (string), `country` (string), `verified_at` (i64), `level` (u8). Encode the layout exactly as `sas-lib` requires for the pinned version (Gate G5). Verified in G5: layout `[12, 12, 12, 8, 0]` (SAS schema data types String, String, String, I64, U8), field names in that order, version 1 (the program creates every schema at version 1), attestation data encoded as Borsh (facts E5). `verified_at` is Unix seconds; `country` is the ISO 3166-1 alpha-2 code from `orgs.country`. `level` 1 means manual review by a Sotto admin (D-09) and 0 the automatic verification of a new organization on devnet, with no review (D-30; the public proof page reads only 1 and above as reviewed); other values are reserved for a KYB provider (Post-hackathon).
- Attestation nonce: the org owner's wallet address, so the attestation is discoverable from `ProofRecord.owner`. Verify in G5 that SAS derives the attestation address from credential, schema and nonce; if not, stop and ask. Expiry: 365 days. **VERIFIED** in G5 (2026-09-27, devnet and localnet, facts E4): the address is the PDA of `["attestation", credential, schema, nonce]` under the SAS program, and the program rejects any other address with `InvalidAttestation` (custom error 2). Closing an attestation needs an authorized signer and returns its rent to the payer.
- Devnet addresses (facts E7): credential `4KX4P7he62x5x8X35vubNNhJRhV4vJXPGNsc8skPyKFT`, schema `A4PX8yuPQYeZFqtPomd5E3Jce7dTuWktcnpzb9YCM4z3`.
- Closing an attestation by hand (step 1.6): `scripts/sas-close-attestation.ts --owner <wallet>`, devnet only, with confirmation. On localnet, `scripts/bootstrap-localnet.ts` creates the credential and schema with a throwaway signer. ## 6. Cross cutting

- Rate limits per IP and per session on auth and write endpoints. Implementation (step 1.2, `apps/web/lib/server/rate-limit.ts`): fixed one minute windows counted in Postgres (`rate_limits`), so every server instance shares them, keyed by an HMAC of the session ID or of the client IP (first `x-forwarded-for` entry). Defaults: auth 20 per IP, writes 60 per session and 120 per IP, `/rpc` 600 per session, since step 2.8 the public proof view 60 per IP, since step 3.2 request access 10 per IP in a one hour window, and since step 4.3 the devUSD faucet 6 requests per session in a one hour window (besides its limit of 10,000 devUSD per wallet per 24 hours), and since step 4.6 the faucet's SOL 3 requests per IP in a 24 hour window, besides that session limit and its own limits (D-31).
- CSRF: SameSite=Lax cookie plus `Origin` header check on every non GET request. The Origin must be the request's own origin or `NEXT_PUBLIC_APP_URL`; a missing Origin is refused (403 `forbidden_origin`).
- Logging: structured JSON, request ID, user ID, org ID. A redaction list blocks fields named like keys, signatures of key derivation messages, ciphertexts and blobs. Implementation (step 1.2, `apps/web/lib/server/log.ts`): one JSON line per request with request ID, method, path, status, duration and user ID; fields whose names match key, secret, signature, ciphertext, blob, seed, mnemonic, password, passphrase, token, cookie, authorization, session, ikm, private or an amount word are replaced, and connection strings, API keys and the configured secret values are removed from every string. Request bodies are never logged. Since step 1.4 an error from a failed query keeps only the statement: Drizzle puts the query parameters (which can be what a user typed, such as a contact email) into its message, so the parameters are cut off, and the database error is logged as its message, code and constraint without its detail (which can repeat the row). The worker's log lines (`apps/worker/src/log.ts`) follow the same rules and also remove database URLs. Since step 2.1 (founder 2026-09-29) bearer tokens in URLs never reach a log: the segment after `/api/invites/` or `/app/invite/` (the invite link token) becomes `:token` in every logged string, the request path included, also when URL encoded (a `?next=` value), in the web app and the worker (`BEARER_PATH_PREFIXES` in `log.ts`); `apps/web/test/log-bearer.test.ts` fails when a dynamic route segment named like a secret is not covered, and the invite API test checks that no log line of a read and an acceptance holds the token.
- Sessions (step 1.2, `apps/web/lib/server/session.ts`): the cookie `sotto_session` holds a random 32 byte token (httpOnly, Secure, SameSite=Lax); the database stores only its HMAC with `SESSION_SECRET`. Idle timeout 12 hours, absolute lifetime 7 days (04 section 5).
- Error reporting service must use the same redaction.
